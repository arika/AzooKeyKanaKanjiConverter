# Mazegaki Vision（交ぜ書き変換）

> **下書き（提案前）** — この文書は upstream への提案を前提にした下書きです。
> 実装はフォークで進めており、方針についてメンテナーのご意見をいただいてから PR を分けて提出したいと考えています。

## 概要

`convertTarget` に漢字とかなが混在した入力（交ぜ書き入力）を、入力された漢字を保ったまま変換できるようにすることを提案します。

| 入力 | 現状の 1 位 | 提案後に期待する候補 |
|---|---|---|
| `破たん` | 破端 | 破綻 |
| `き損` | 機損 | 毀損 |
| `四面そ歌` | 四面粗歌 | 四面楚歌 |
| `彼の判断はし意的だ` | 彼の判断はし意的だ | 彼の判断は恣意的だ |
| `機のう` | 機能 | 機能（**帰納・昨日は出さない**） |

既定では無効にし、無効のときの挙動と性能は現状と同一にします。

## 動機

### 漢字直接入力（漢直）

T-Code や TUT-Code などの漢直では、利用者は覚えている字を漢字のまま打ち、覚えていない字だけをかなで打ちます。
そのため、入力には交ぜ書きが日常的に現れます。
カスタム入力テーブル（v0.10.0〜）を使えば、漢直のキー列 → 漢字の対応をそのまま書けるので、
変換エンジン側が交ぜ書き入力を扱えれば、漢直の IME をこのライブラリの上に作れます。

### その他の用途

- かな入力の途中で、読みの分からない字だけを漢字で貼り付けたり、手書き入力で入れたりする。
- 新聞などの交ぜ書き表記（`改ざん`、`けん引`）を、通常の表記に直す変換を候補として出す。
- 部首入力・手書き入力など、漢字を直接出力する入力方式との併用。

## 現状の挙動

辞書は `convertTarget` をカタカナにした文字列をキーにして引くため、漢字を含む範囲は辞書にヒットしません。
漢字は `getWiseDicdata` などが作る素通しのノードとしてラティスに入り、かなの部分だけが独立に変換されます。

その結果、次のようになります。

- `破たん` は「破」+「たん→端」になり、「破綻」は出ない。
- Zenzai を有効にすると一部は改善します。ただし、入力された漢字に対して文脈上もっともらしい別の字を選ぶことがあり（`し意的` → `私意的`、`ふん糾` → `分糾`）、誤字が 1 位に出ます。

## 提案

### 方式

辞書を引く段階で、入力漢字を読みに展開したキーでも辞書を引きます。
返ってきた辞書語は、**入力漢字がその読みの位置に現れる**ものだけを残します。

```
convertTarget: 破たん
  └ lookupDicdata(surfaceRange: 0..<…)
       SurfaceGenerator:  ハ? → 破 / 破タ / 破タン      （既存。ヒットしない）
       MazegakiGenerator: ハ / ハタ / ハタン / ヤブ / …   （新規。破 = [0,1) の制約付き）
       → 辞書語 破綻(ハタン) ✓  破端(ハタン) ✓  は単(ハタン) ✗（破が無い）
```

- 展開は `lookupDicdata` の 1 回の呼び出しが辞書を引く範囲の中だけで行います。
  組み合わせの数は「その範囲に含まれる入力漢字の読みの数」の積で抑えられ、文全体での組み合わせの爆発は起きません。
- LOUDS の `MovingTowardPrefixSearchHelper` と `setUnreachablePath` を使い、辞書に存在しない読みの枝を早く刈ります。
- 辞書語は本来の ruby（例: ハタン）を持ったままラティスに入ります。学習データの形式は変わりません。
- 素通しのノードは残します。展開で該当する語がない場合の受け皿になります。

### 整合判定

辞書語の word / ruby と、その語の範囲にある制約から、word の各文字を ruby の部分列に対応づけられるかを判定します。

1. かなは ruby と 1 文字ずつ一致すること。
2. 制約の位置では、word の文字が入力漢字と一致し、ruby のちょうどその範囲に対応すること。
3. その他の文字（漢字など）は ruby の 1〜4 文字に対応してよい。ただし、制約の開始位置をまたいではならない。
4. 制約が語の境界をまたぐ語は不適合とする。

#### 「同じ字」の判定（正準等価）

規則 2 の「入力漢字と一致」は、Unicode の正準等価で判定します（Swift の `Character` の `==` と同じ）。
不変条件の「入力した漢字が別の字に置き換わる候補を出さない」も、「正準等価でない字に置き換わる候補を出さない」という意味です。

- 例: `神`（U+795E）を入力すると、U+795E を含む語と、CJK 互換漢字の `神`（U+FA19）を含む語の両方が候補になります。逆も同じです。
- 正準等価でない異体字（`桜`→`櫻`、`高`→`髙`）は別の字として扱い、候補から除きます。
- 正規化しても変わらない互換漢字のブロックの字（`﨑` U+FA11、`﨟` U+FA1F）は、独立した字として扱います。

理由:

- 互換漢字と対応する統合漢字は、Unicode では同じ抽象文字です。NFC で正規化すると区別が消えるため、入力の経路によっては、利用者が打ち分けても区別が残りません。
- 既定辞書には互換漢字が 70 種類・331 か所あります（U+FA19 は 20 か所）。スカラー値で厳密に比べると、統合漢字で入力した利用者に、これらの語が出なくなります。
- 字形を指定する仕組みは異体字セレクタ（IVS）であり、互換漢字ではありません。

未対応: 異体字セレクタ付きの入力（例: `神` U+795E U+FE00）は、`Character` としてはセレクタなしの字と別の字になるので、読み表を引けず、展開しません（素通しのまま）。

### 読みの供給

漢字の読みのデータはライブラリに同梱せず、クライアントから受け取ります（ライセンスの判断をクライアントに委ねるため）。

```swift
public struct MazegakiMode: Sendable, Equatable {
    public static let off: MazegakiMode
    /// 1 行 1 字の TSV（漢字<TAB>読み1,読み2,…。読みはカタカナで、優先度の順）
    public static func on(readingTableURL: URL, maxReadingsPerKanji: Int = 8) -> MazegakiMode
}

// ConvertRequestOptions.init に `mazegakiMode: MazegakiMode = .off` を追加する（既定値つきなので、既存の呼び出し側は変更不要）
```

- 読みの派生（促音化: 学 ガク→ガッ、連濁: 社 シャ→ジャ）は、ライブラリ側で生成し、ペナルティを付けます。
- TSV の形式の代わりに、プロトコル（`MazegakiReadingProvider`）で受け取る形も検討しています。

### 影響を受ける既存の処理

交ぜ書きノードでは「ruby の連結が `convertTarget.toKatakana()` と一致する」という前提が崩れます。
現在、この前提に依存していると把握している箇所は次のとおりです。

| 箇所 | 影響 | 対応案 |
|---|---|---|
| `KanaKanjiConverter` の `checkRuby`（完全一致の候補を上位 3 位に入れる処理） | 交ぜ書きの候補が完全一致と判定されず、値の低い素通しの候補（`けん引` → `県引`）が 3 番目に割り込む | 表層と ruby を読み表で突き合わせて判定する |
| `Prediction.getPredictionCandidates` の `lastRuby` | 読みを `convertTarget` から作っているので、漢字を含む文節から予測できない | 最後の文節の候補の ruby を使い、予測した語に入力漢字の制約をかける |
| `ZenzaiCache.getNewConstraint` | `hasPrefix(item.ruby)` が成り立たない | 表層と ruby を読み表で突き合わせて位置を対応づける（`Candidate` の語は `LatticeRange` を持たないため） |
| Zenzai のプロンプト | 漢字を含む入力が渡り、モデルは漢字の読みを知らないまま、かなの部分だけで判断する（`けん引` → `検` + `引`） | 評価する候補の ruby を入力として渡す（下の「Zenzai との併用」を参照） |

#### Zenzai との併用

Zenzai を使うかどうかは、これまでどおり `zenzaiMode` の指定に従います。交ぜ書きの入力では、モデルに入力の代わりに、評価する候補の ruby を渡します（案B）。入力を漢字が混ざったまま渡す方法（案A）と比べました。

| 方式（zenz-v3.2-small、CPU、inferenceLimit 5、1 文字ずつ入力） | 自作 52 件 1位 / 5位以内 | mazegaki-dic 由来 3,000 件 1位 / 5位以内 | 文の 1 打鍵の平均 |
|---|---|---|---|
| 案A: 入力を漢字のまま渡す | 21 / 36 | 1,510 / 2,301 | 12.5ms |
| 案B: 候補の ruby を渡す | 36 / 45 | 1,976 / 2,477 | 13.6ms |
| （参考）Zenzai オフ | 45 / 51 | 2,702 / 2,897 | 3.3ms |

- 案B では、プロンプトが候補ごとに変わるので、KV キャッシュを使い回せる場面が減ります。
- どちらの方式でも、Zenzai をオフにした場合より 1 位が少なくなります。原因は調査中です。入力漢字の消失はどちらも 0 件です。

#### 予測変換を候補に混ぜる場合の並び

予測変換を候補に混ぜる設定（`.autoMix`）では、交ぜ書きの入力に限り、入力全体を変換した最良の候補を先頭に置き、予測変換の候補はその後に並べます。かなの入力の並びは変えません。

- 上の対応で交ぜ書きの文節からも予測変換が出るようになると、正解の語を前に含む予測（`けん引` → `牽引車`、`ら致` → `拉致事件`）が先頭に来ることが多くなりました。かなの入力でも同じことが起きますが（`はたん` → `破綻し`）、交ぜ書きの入力では利用者が漢字をはっきり打っているので、打ったとおりの変換を優先する方が自然だと考えました。
- 評価（Zenzai オフ、1 文字ずつ入力）: 自作の 52 件で 1 位 25 → 45、mazegaki-dic 由来の 3,000 件で 1 位 1,970 → 2,702。予測変換は 2 位以降に残ります。
- 予測変換の候補が上位 5 件の枠を使うので、入力全体の変換の 2 番手以降が押し出されることがあります（3,000 件中、5 位以内から外れたもの 6 件）。かなの入力でも同じ性質です。

## 事前検証

フォーク上で、エンジンの外に同じ方式を実装して評価しました（外付け実装）。
外付け実装では、漢字の読みの組み合わせごとに変換を呼び出して、結果を絞り込んでいます。
評価データは自作の 52 件で、前の文脈なし・学習なしの条件です。

| 方式 | エンジン | 1位 | 5位以内 | 圏外 | 平均 / 最大 |
|---|---|---|---|---|---|
| 現状（素通し） | main（fddde10） | 7 | 16 | 36 | 0.9ms / 2.9ms |
| 外付けの交ぜ書き | main（fddde10） | **46** | **49** | 3 | 42ms / 225ms |
| 現状（素通し） | 0.11.2 | 10 | 16 | 35 | 0.8ms / 2.1ms |
| 現状 + Zenzai（CPU） | 0.11.2 | 20 | 21 | 30 | 7.4ms / 14ms |

計測環境: Apple M2 Pro / macOS 27 / release ビルド。
時間は素通しが最後の 1 打鍵ぶん、外付けが最終的な入力を 1 回変換するのにかかった時間。

- 入力漢字は制約として正しく効きました（`機のう→機能`、`こう成→構成`）。入力漢字を含まない候補は 1 件も出ませんでした。
- 外付け実装は組み合わせごとに変換を呼ぶため、文単位では 100ms 以上かかります。これが、辞書引きの段階に組み込むことを提案する理由です。
- 熟字訓（`昨のう→昨日`）は 1 字ずつの読みに分けられないので、対象外とします。

評価用のテストケースと計測ツールは、PR に合わせて提出できます（形式はご相談したいです）。

## 互換性と性能

- `mazegakiMode: .off`（既定）のときは、新しいコードの経路を通らないようにします。変換結果と性能が変わらないことを計測して示します。
- `.on` でも、漢字を含まない入力では生成器が何も生成しないので、追加の負荷はほぼない想定です。
- 漢字を含む入力の性能は、読みの多い字が続く場合が最悪のケースです。PR の際に計測値を示します。

## PR の分け方（案）

1. `MazegakiMode` の API と読み表のローダ（挙動の変更なし）
2. `MazegakiGenerator` と整合判定による辞書引き（中心となる変更）
3. ruby と `convertTarget` の一致を前提にした箇所の修正（`checkRuby`、予測変換、Zenzai の制約）
4. Zenzai との統合（方針が決まってから）

## 相談したいこと

1. **この機能をライブラリで受け入れていただけるか。** クライアント側で実装すべき機能だというお考えであれば、その方針に従います。
2. **API の形。** `ConvertRequestOptions` に足すか、`ComposingText` の側で入力漢字を明示するか。読み表は URL で受け取るかプロトコルで受け取るか。
3. **Zenzai のプロンプトの扱い。** 評価する候補の ruby を渡す方式（案B）にしました（上の「Zenzai との併用」を参照）。KV キャッシュの効率が下がることと、Zenzai オフより精度が下がることについて、ご意見を伺いたいです。
4. **評価データとツール。** テストケースを `Tests/` に入れるか、CLI（`anco`）にオプションを足すか。
5. **「同じ字」の判定。** 入力漢字と辞書語の字を正準等価で比べています（上の「「同じ字」の判定」を参照）。スカラー値で厳密に区別すべきだというお考えがあれば伺いたいです。
6. **予測変換の並び。** 交ぜ書きの入力では、予測変換を混ぜる設定でも入力全体の変換を先頭に置いています（上の「予測変換を候補に混ぜる場合の並び」を参照）。かなの入力とそろえるべきだというお考えがあれば伺いたいです。
